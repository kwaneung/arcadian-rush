# 05 공식 기록

상태: 리뷰 전. 잠기기 전에는 구현하지 않는다.

## 목적

서버가 Neon에 직접 쓴 종료 행만 공식 기록으로 남기고, 그 목록을 보여 준다.

## 입력

- 계약의 Neon 스키마와 `RunStore`
- 서버 환경 변수 `DATABASE_URL`
- 종료 절차의 `finish`
- `GET /api/records`와 `GET /api/runs/:id`

브라우저가 보내는 생존 시간, 처치 수, 레벨은 입력으로 쓰지 않는다.

## 규칙

- 공식 기록 모드의 저장소는 Neon이다. 메모리 저장소를 이 모드에 연결하지 않는다.
- 발급 때 행이 생긴다. 위치, 체력, 적, 투사체, 경험치, 등급은 열로 두지 않는다.
- 점수가 채워지는 때는 `active`에서 `ended`로 바뀌는 `finish` 한 번이다.
- `POST`, `PUT`, `PATCH`, `DELETE`를 `/api/records`와 `/api/runs/:id`에 보내면 405다. 본문에 점수가 있어도 행은 바뀌지 않는다.
- 목록과 단건 조회 응답에는 토큰, 해시, 주소 해시, `DATABASE_URL`이 없다.
- 단건 조회는 `ended`이면서 종료 제약이 채워진 행만 점수를 돌려준다. `issued`와 `active`는 상태만 돌려준다.
- 클라이언트가 끊긴 뒤 하는 단건 조회는 한 번이다. `recorded`에 해당하는 종료 행일 때만 결과 숫자를 그린다.
- 발급 제한은 저장소의 행 수로 센다. 인스턴스 메모리 카운터만으로 공식 모드의 제한을 대체하지 않는다.
- `sim_ms`를 갱신하는 코드는 `src/server/store`에만 둔다.

## 완료 조건

자동 테스트:

1. 스키마를 적용한 저장소에서 `issue` 하나, 성공한 `activate` 하나, `finish` 하나가 행을 `ended`로 만들고 `sim_ms`, `kills`, `level`, `end_reason`이 인자와 같다.
2. 같은 `finish`의 두 번째 호출은 `unrecorded`이고 행의 점수는 처음 값이다.
3. 활성화 전에 보낸 `finish`는 행을 `ended`로 만들지 않는다.
4. 만료된 발급과 이미 활성화된 발급은 `activate`가 `reject`다. 서로 다른 두 프로세스에서 같은 토큰을 활성화해도 성공은 하나다.
5. 60000ms 안의 6번째 발급은 `rate`이고 행 수가 5를 넘지 않는다.
6. `board`는 `ended`만 반환한다. 정렬은 `sim_ms` 내림차순, `kills` 내림차순, `ended_at` 오름차순이고 기본 20개, 요청 50 초과는 50개다.
7. `active`로 남은 행은 `board`에 없다.
8. 점수 필드를 넣은 `POST /api/records`는 405이고 위 행의 점수는 그대로다.
9. `GET /api/runs/:id`의 종료 응답은 행의 세 점수와 이유와 시각만 더한다.
10. 클라이언트 청크에 `DATABASE_URL` 값과 서버 저장소 모듈이 없다.
11. 슬라이스 1부터 4의 자동 테스트가 저장소를 Neon 구현으로 바꿔도 권한 규칙은 그대로 통과한다. 기록 여부만 `recorded`로 바뀐다.

화면 확인:

1. 한 판이 사망 또는 제한 시간으로 끝나면 결과의 생존 시간, 처치 수, 레벨이 그 판의 Neon 행과 같다. `recorded`가 참이면 `기록되지 않음`은 나오지 않는다.
2. `/records`는 그 공식 목록만 보여 준다. 행이 없으면 빈 목록이다.
3. 연결이 끊긴 판은, 조회 결과가 종료 행일 때만 그 숫자를 보여 준다. 조회가 `active`이거나 실패하면 `연결이 끊겼습니다`만 남는다.
4. 브라우저에서 결과 숫자의 DOM을 바꾼 뒤 목록을 다시 열어도 서버 행과 같은 값이 나온다.

## 범위 밖

계정, 이름, 리더보드 조작 방지용 봇 판별, `active` 행 청소, 15분과 30분 런.
